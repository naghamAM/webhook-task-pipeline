Mental Model

What The App Actually Is

Think of this project as a very small event automation platform. A pipeline connects:

  • A source URL that receives incoming webhook events
  • A processing action that transforms the payload
  • One or more subscriber URLs that receive the transformed result

The key architectural choice is that webhook ingestion is fast and asynchronous. The API does not do processing inline. It only saves the job, and the worker handles the slow work later.

Core Flow

End-To-End Request Lifecycle

Pipeline setup

A user creates a pipeline with `source_key`, `action_type`, `action_config`, and `subscriber_urls`.

Webhook ingestion

`POST /webhooks/:sourceKey` finds the pipeline and inserts a new job with status `pending`.

Worker claims work

The worker atomically updates the next `pending` job to `processing` using SQL and `FOR UPDATE SKIP LOCKED`.

Payload processing

The worker runs one of three action types: `add_field`, `uppercase_name`, or `filter_fields`.

Subscriber delivery

The worker POSTs the processed payload to each subscriber with retry logic and request timeout handling.

Observability

Every delivery attempt is saved in the database, and the job ends as either `completed` or `failed`.

Code Map

Where To Read What

`src/app.ts`

API entry point. Contains health check, pipeline CRUD, webhook ingestion, job lookup, and delivery-attempt endpoints.

`src/server.ts`

Thin bootstrap that starts the Express app on the configured port.

`src/worker/worker.ts`

Main background loop. Claims jobs, processes payloads, records attempts, and updates final job status.

`src/worker/process-job.ts`

Pure transformation logic for the three action types. This is the easiest file to explain in an interview.

`src/worker/deliver.ts`

Subscriber delivery logic. Handles timeouts, retries, success, and failure results.

`src/pipelines/validation.ts`

API validation rules. This file explains why invalid pipeline definitions are rejected before the worker sees them.

`src/db/schema.sql`

Main schema: pipelines, subscribers, jobs, delivery_attempts.

`docker-compose.yml`

Local runtime shape. Postgres, migration job, API server, and worker come up together.

Database

Data Model You Should Be Able To Explain

`pipelines`

Stores the pipeline definition: the source key, the selected action, and the config for that action.

`subscribers`

Stores destination URLs for each pipeline. One pipeline can have many subscribers.

`jobs`

Stores inbound webhook events, current job status, processed payload, and any top-level error message.

`delivery_attempts`

Stores each retry attempt so you can inspect failure history and prove retry behavior works.

Evaluator Q&A

Questions You Are Likely To Get

Why did you separate the API and worker?

So webhook ingestion stays fast and reliable. The API just validates input and stores a job. Processing and delivery are slower operations and belong in the background worker.

Why use PostgreSQL as the queue?

It keeps the project small, easy to run, and aligned with the assignment. PostgreSQL already stores the app data, and it can support a simple pending-job queue for this scope.

How do you avoid processing a job twice?

The worker claims jobs with an atomic SQL update and `FOR UPDATE SKIP LOCKED`. That reduces the chance of two workers taking the same pending job.

What happens if delivery fails?

The worker retries up to three times, stores each attempt in `delivery_attempts`, and marks the job as `failed` if delivery still does not succeed.

How do you validate pipeline definitions?

The API uses `zod` validation. It checks general shape and also action-specific config rules, like requiring `fieldName` for `add_field` and `allowedFields` for `filter_fields`.

Why store delivery attempts separately from jobs?

Because job-level status is not enough to debug failures. A separate attempts table preserves retry history and gives much better observability.

What are the three processing actions?
  • `add_field`: adds a configured field/value to the payload
  • `uppercase_name`: uppercases `payload.data.name`
  • `filter_fields`: keeps only configured top-level fields
What did you do for reliability?
  • Asynchronous processing instead of inline webhook work
  • Atomic job claiming
  • Retries for subscriber delivery
  • Request timeouts for outbound delivery
  • Persisted error messages and attempt history
  • Transactional pipeline create/update operations
What would you improve next?

Replace DB polling with a dedicated queue, add authentication or webhook signatures, and expose richer subscriber-level job summaries.

What is the easiest way to explain the worker file?

Say it in four verbs: claim, process, deliver, record. The worker claims a job, processes the payload, delivers it to subscribers, and records both final job state and attempt history.

Study Plan

Key Topics To Learn Before The Demo

Express request lifecycle

Know how requests enter `app.ts`, how params and body data are used, and where responses are returned.

PostgreSQL basics

Understand the tables, foreign keys, and why the app stores jobs and attempts separately.

Background job processing

Be able to explain why asynchronous workers are useful and why they are better than processing the webhook inline.

Retry logic and timeouts

Know why retries exist, why timeouts matter, and what happens after repeated delivery failures.

Validation with Zod

Understand why validation belongs at the API boundary and what action-specific validation this app performs.

Docker Compose flow

Be ready to explain the four services: `postgres`, `migrate`, `server`, and `worker`.

CI workflow

The pipeline installs deps, builds the project, runs tests, validates Compose, and builds the Docker image.

Tradeoffs

Practice explaining that this is intentionally simple and that some production-grade improvements were left for future work.

Demo Coaching

Best 3-Minute Architecture Explanation

1. This app lets users define pipelines.
2. Each pipeline has a source key, a processing action, and subscriber URLs.
3. When a webhook hits the source URL, the API stores a pending job in PostgreSQL.
4. A separate worker claims that job in the background.
5. The worker transforms the payload and sends it to subscribers.
6. Each delivery attempt is stored, and the job ends as completed or failed.
7. Docker Compose runs the full stack, and CI verifies build, tests, and Docker config.

Strengths

What You Should Emphasize

  • Clear separation between API and worker responsibilities
  • Reasonable schema design for the project scope
  • Observable retry behavior through persisted delivery attempts
  • Validation at the API layer instead of trusting raw input
  • Reproducible local setup with Docker Compose and CI
Weak Spots

Be Honest If Asked

  • PostgreSQL polling is simpler than a real message queue
  • No auth or signature verification yet
  • No metrics or dashboard
  • Tests focus on core behavior, not full API integration
Demo Tips

How To Sound Confident

  • Talk in flows, not files, first
  • Explain the why behind each decision
  • Use concrete examples from a webhook payload
  • Say what you simplified and why
  • Keep future improvements realistic and specific
